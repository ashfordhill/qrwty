# Generated local v2 foundation

Experimental provider/project foundation. Inspect .jeeves/report.json for missing features and hooks. No application readiness or strict certification is claimed.

Node 24.21.0 and pnpm 12.16.1. Run `pnpm install --frozen-lockfile` then `pnpm build`. `package.json`, `pnpm-lock.yaml` and `pnpm-workspace.yaml` are yours: add a package with `pnpm add <name>@<exact version>`. `pnpm-workspace.yaml`'s `allowBuilds` says which packages' install scripts run: the template's dependencies run none (`protobufjs: false`), so neither command needs `--ignore-scripts`. Set a unique `COMPOSE_PROJECT_NAME` and three distinct free loopback ports: `LOCAL_HTTP_PORT`, `LOCAL_IDENTITY_PORT`, `LOCAL_OBJECT_PORT`. Run `pnpm first-run` once, `pnpm stop` to stop all profiles and `pnpm start` for normal restart. Reuse those exact values and private .runtime with the original Docker volumes. No resets or credential rotation occur. An interrupted single-use storage bootstrap requires manual inspection.

**Your own configuration.** `compose.override.yaml` beside `compose.yaml` is yours: export never writes it and `update:v2` never touches it. Docker Compose merges it into every command `pnpm first-run`, `start` and `stop` run, so give your modules their own `environment` and `secrets` there, or add a service of your own (for example a scheduler that calls your routes). A service of your own starts with `pnpm start` only when a generated service `depends_on` it, which your override may add; otherwise start it with your own `docker compose up`. Don't redefine a generated service's image, command, ports or healthcheck. A change applies at the next `pnpm start`.

Migration owners/admin are mounted only into setup. `scripts/migrate.mjs` reaches PostgreSQL at `PGHOST` and `PGPORT` with `JEEVES_MIGRATE_TLS` (`disable`, or `verify-full` with an optional `JEEVES_MIGRATE_CA_FILE` and `JEEVES_MIGRATE_TLS_SERVERNAME`), read as a database's `_TLS` is; `PGSSLMODE` can't change it, and with `JEEVES_REQUIRE_TLS=true` it must be `verify-full` unless `PGHOST` is a socket directory. A credential is read from `JEEVES_SECRET_<NAME>_FILE` when that is set (an absolute path; `<NAME>` is the secret's name upper-cased, with `-` and `.` as `_`), else from `SECRET_DIR/<name>` (`/run/secrets/<name>`, where Compose mounts it). Runtime logins receive no implicit table access; features contribute explicit relation/view grants. PostgreSQL names are quoted and provider/composed-name limits refuse rather than truncate. Storage originals remain private; local public websites are a declared local-security limitation.

Cleanup only an owned disposable export: `docker compose --profile '*' down --volumes --remove-orphans` with its recorded project/ports, then remove its .runtime. Never run cleanup against a retained runtime.

Runnable processes: each application tile runs as `app-<id>` from `src/processes/<id>.ts`, healthy once its ready marker exists; HTTP processes answer `GET /healthz` on port 3000 inside the Compose network. `app-edge` publishes each public HTTP process at `http://127.0.0.1:$LOCAL_HTTP_PORT/api/<id>/` and answers `GET /healthz` itself; internal ones are reached only inside the network at `http://app-<id>:3000`. A module's routes are under `/modules/<module id>`: a stub or a generated hook in `src/modules/` answers 501 `NOT_IMPLEMENTED` until you write it. A consumer module or worker template runs a loop on its queue (a topic's `<topic>--<id>` subscriber): "Not implemented" sends the message to `<queue>.failed` with one log line, other errors retry within the loop's limit (a stub's 5 times, waiting 250 ms doubling up to 10 s), an unreachable store waits 5 s and keeps the attempt, a failed `fetch` to an outside host keeps the normal retries, and `pnpm stop` drains the loops. Every store or channel a stub links to is provisioned for its tile with its links' widest access (a database login with CONNECT and USAGE on public, SELECT on the database's `published` views and on another owner's template views; a queue, topic or subscriber; a cache; a bucket key; a search service with no index), and `src/runtime/module-clients.ts` gives each stub real clients, each probed once at startup. A database a stub writes also has Jeeves's own `jeeves.idempotency_records` (`infra/postgres/<database>/050-jeeves-idempotency.sql`), which only the logins of the tiles whose stubs write it use: a stub's `idempotent(...)` keeps a 200–299 answer per scope and key for 24 hours and replays it for the same request (`requestHash` in `src/runtime/idempotency.ts`), a different request under the key throws `IdempotencyConflict`, and expired records are swept every 60 s. Each stub declares the settings it reads in its file's `settings` export (`declareSettings` with `text()`, `integer()`, `url()`, `secret()`, `keyRing()` and `optional(kind)` from `src/runtime/settings.ts`); its process reads them in its configuration pass, before any client is built or probed, and gives them to the stub as `dependencies.settings`: a missing or invalid one fails startup with `Invalid setting <NAME>`, never its value. `compose.yaml` sets none of them: set a setting in `compose.override.yaml`'s `environment`, and a `secret()` or `keyRing()` as a file read as a credential is (above), `<name>` being the setting's name lower-cased with `_` as `-` (`PROBE_TOKEN` is `probe-token`), through its `secrets`; `processes.tiles[].stubSettings` in .jeeves/report.json names the files each process reads them from. Each module that writes a database has its own SQL file, `infra/postgres/<database>/modules/<module>.sql`, yours to write: `first-run` and `start` run it every time, after the template migrations and views, as the setup-only owner in schema `m_<module>`, so keep it re-runnable (`IF NOT EXISTS`, `CREATE OR REPLACE`). Only its tile's login uses that schema; every login on the database may SELECT what it publishes as views in `published`, and nothing else of its tables. `first-run` and `start` start them only while `processes.runnable` in .jeeves/report.json is true; its `processes.tiles` lists each process's routes, loops and provisioned stores. No restart policy: a failed process stays exited until `pnpm start`.

**Endpoints from the environment.** Each process with stubs checks the endpoints its clients and sign-in use in one pass before any client is built or probed, and reads each again as it builds that client, with no default: `JEEVES_DATABASE_<ID>_HOST` (a host, or an absolute Unix socket directory) and `_PORT` for each database, `JEEVES_CACHE_<ID>_HOST` and `_PORT` for each cache, `JEEVES_BROKER_HOST` and `JEEVES_BROKER_PORT` for the broker, and `JEEVES_TILE_<ID>_URL` (absolute `http:` or `https:`, with no credentials, query, fragment or whitespace) for each tile its stubs call, where `<ID>` is the tile ID upper-cased with `-` as `_`. A process that publishes to or consumes a Pub/Sub topic reads `JEEVES_PUBSUB_PROJECT`, a Google Cloud project ID (a lowercase letter, then up to 29 lowercase letters, digits or `-`, optionally after `<domain>:`); `compose.yaml` also sets `PUBSUB_EMULATOR_HOST` for the local emulator and `METADATA_SERVER_DETECTION: none`, so the client looks for no Google metadata server; a deployment leaves both unset. Each External API its stubs call is at `JEEVES_EXTERNAL_<ID>_URL`, by the same URL rule, which `compose.yaml` doesn't set: the value is yours, so set it in `compose.override.yaml` (and in your deployment); until it is set the process fails startup with `Invalid endpoint JEEVES_EXTERNAL_<ID>_URL`. A failed call to an External API keeps a loop's normal retries. A process whose stubs call the Identity reads `JEEVES_IDENTITY_<ID>_URL`, the Identity's base URL as the process reaches it, by the same URL rule: `compose.yaml` sets Keycloak's address inside the network, `http://identity-<id>:8080` (a stub adds the realm's paths, `/realms/<id>/...`); a deployment sets its issuer's origin, or another address its processes reach. A sign-in's `OIDC_ISSUER` is what tokens carry, which a container can't reach locally, so it isn't the client's base. A lost connection to the Identity waits as an unreachable store's does. A missing or invalid one fails startup with `Invalid endpoint <variable>`, never its value (several at once: `Invalid configuration: <message>; <message>`). Each database and cache also reads its transport, `JEEVES_DATABASE_<ID>_TLS` or `JEEVES_CACHE_<ID>_TLS`, with no default: `disable` (plain text, which `PGSSLMODE` can't change) or `verify-full` (TLS that checks the certificate chain and the host name); with `verify-full`, `_CA_FILE` is an optional PEM file (else Node's roots; one that can't be read fails startup with `Unreadable CA file <variable>`) and `_TLS_SERVERNAME` the optional name the certificate carries when it isn't the host (a managed instance reached by a private address). With `JEEVES_REQUIRE_TLS=true` (else unset), startup fails with `Insecure endpoint <variable>` for a database or cache whose transport isn't `verify-full` (a database's Unix socket directory is local transport and passes), a `JEEVES_TILE_<ID>_URL`, `JEEVES_EXTERNAL_<ID>_URL`, `JEEVES_IDENTITY_<ID>_URL`, `OIDC_ISSUER` or `OIDC_JWKS_URL` that isn't `https:`, and any `PUBSUB_EMULATOR_HOST`; the broker, object storage and search are plain text and aren't checked. With the switch, `NODE_TLS_REJECT_UNAUTHORIZED` must be unset or `1`, else startup fails with `Insecure endpoint NODE_TLS_REJECT_UNAUTHORIZED`: `0` would turn off certificate checks for every client that leaves them to Node. `compose.yaml` sets the local values (`disable`, and no `JEEVES_REQUIRE_TLS`); a deployment sets its own. Object storage and search are still reached at their local names. Each process reads (also `processes.tiles[].environment` in .jeeves/report.json):

- `app-account-api`: `JEEVES_DATABASE_ANALYTICS_HOST`, `JEEVES_DATABASE_ANALYTICS_PORT`, `JEEVES_DATABASE_ANALYTICS_TLS`, `JEEVES_DATABASE_LINKS_HOST`, `JEEVES_DATABASE_LINKS_PORT`, `JEEVES_DATABASE_LINKS_TLS`, `JEEVES_TILE_BILLING_API_URL`, `OIDC_AUDIENCE`, `OIDC_ISSUER`, `OIDC_JWKS_URL`
- `app-analytics-worker`: `JEEVES_DATABASE_ANALYTICS_HOST`, `JEEVES_DATABASE_ANALYTICS_PORT`, `JEEVES_DATABASE_ANALYTICS_TLS`, `JEEVES_PUBSUB_PROJECT`, `METADATA_SERVER_DETECTION`, `PUBSUB_EMULATOR_HOST`
- `app-billing-api`: `JEEVES_DATABASE_BILLING_HOST`, `JEEVES_DATABASE_BILLING_PORT`, `JEEVES_DATABASE_BILLING_TLS`, `JEEVES_EXTERNAL_STRIPE_API_URL`, `OIDC_AUDIENCE`, `OIDC_ISSUER`, `OIDC_JWKS_URL`
- `app-link-api`: `JEEVES_CACHE_ADMISSION_CACHE_HOST`, `JEEVES_CACHE_ADMISSION_CACHE_PORT`, `JEEVES_CACHE_ADMISSION_CACHE_TLS`, `JEEVES_DATABASE_LINKS_HOST`, `JEEVES_DATABASE_LINKS_PORT`, `JEEVES_DATABASE_LINKS_TLS`, `JEEVES_EXTERNAL_REPUTATION_API_URL`, `JEEVES_TILE_BILLING_API_URL`, `OIDC_AUDIENCE`, `OIDC_ISSUER`, `OIDC_JWKS_URL`
- `app-redirect-service`: `JEEVES_CACHE_HOT_ROUTES_HOST`, `JEEVES_CACHE_HOT_ROUTES_PORT`, `JEEVES_CACHE_HOT_ROUTES_TLS`, `JEEVES_DATABASE_LINKS_HOST`, `JEEVES_DATABASE_LINKS_PORT`, `JEEVES_DATABASE_LINKS_TLS`, `JEEVES_PUBSUB_PROJECT`, `METADATA_SERVER_DETECTION`, `PUBSUB_EMULATOR_HOST`
- `app-session-api`: `JEEVES_DATABASE_SESSIONS_HOST`, `JEEVES_DATABASE_SESSIONS_PORT`, `JEEVES_DATABASE_SESSIONS_TLS`, `JEEVES_IDENTITY_IDENTITY_URL`, `JEEVES_TILE_ACCOUNT_API_URL`, `JEEVES_TILE_BILLING_API_URL`, `JEEVES_TILE_LINK_API_URL`

**Google Cloud Pub/Sub.** A queue only stubs use, saved with provider Google Cloud, is a Pub/Sub topic named by the queue's ID (`click-events`). A stub publishes through the official client (`pubsubPublisher` in `src/runtime/module-clients.ts`): `publish` resolves only once Pub/Sub has acknowledged the message, which carries the module's `messageId` (else a fresh one) as its `messageId` attribute; Pub/Sub gives a resent message a new ID, so a consumer deduplicates on the attribute. A publish fails after 2000 ms, and while 1000 are outstanding the next fails at once. Each publishing process checks at startup that its topic exists and fails without it; it needs `pubsub.topics.get` and `pubsub.topics.publish` on the topic, through Application Default Credentials (the export holds no key file). Processes never create or change topics or subscriptions. Locally `local-pubsub` runs the Pub/Sub emulator, reached only inside the network at `local-pubsub:8085`, and `setup-pubsub` (`scripts/pubsub-init.mjs`) creates every topic and subscription `infra/local.json` lists before the processes start, at `first-run` and every `start`: it creates what is missing and stops, naming it, at one that exists with other settings. Each loop stub that consumes a topic gets its own subscription, `<topic>--<tile>--<module>`, which its tile's copies share (every other loop stub, of this tile or another, gets its own, so each gets every message, in either mode), with a 60 s ack deadline, retries backing off from 1 s to 10 s and dead-letter topic `<subscription>.failed` after 100 delivery attempts, plus a pull subscription `<subscription>.failed` to inspect it. A loop stub on a topic consumes its own subscription through the official client (`pubsubLoop` in `src/runtime/module-clients.ts`), with a RabbitMQ loop's contract: one streaming-pull subscriber holding at most its Worker's Concurrency messages in hand, each acknowledged only after the stub resolves. Another error is nacked, and the subscription's retry policy spaces the redelivery (no 250 ms wait); a failure on delivery attempt 6, after 5 retries, ends the message in `<subscription>.failed` as "Not implemented" does at once: a copy with its attributes and `x-terminal-code`, then the message is acknowledged once Pub/Sub has the copy, else nacked. An unreachable store keeps the message and runs it again 5 s later with the same attempt. A message's attempt is Pub/Sub's delivery attempt, which every redelivery counts, a nack while draining or a lost lease too. A lost subscriber is reported once and reopened 5 s later. Each consuming process checks at startup that its subscription exists, and needs `pubsub.subscriptions.get` and `pubsub.subscriptions.consume` on it and `pubsub.topics.publish` on its `.failed` topic. The emulator keeps nothing across a restart, no topic, subscription or message: a local limit, never a durability claim. A deployment's own infrastructure creates the same topics and subscriptions, and grants the Pub/Sub service agent what a dead-letter policy needs (publish on each `.failed` topic, subscribe on its subscription).
